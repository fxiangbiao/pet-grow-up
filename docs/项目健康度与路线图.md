## 三、文档 vs 实现：4 处必须修正的矛盾

1. **题库数量**：README 写 502 题，实测 **387 条**（差 ~23%）。
2. **数据表数量**：v2.0 文档写"现有 20 张表"，实测 **28 张** —— v2 作者基于旧状态写作，计划里的"在 20 张表基础上扩展"已不准确。
3. **"P0/P1 全部 ✅" 具有误导性**：系统功能确实实现了，但 v2 自己诊断的体验问题（静态宠物、关卡是"读文本+做题"套壳、反馈延迟、无差异化养成）一个都没解决。所谓"完成"是**系统层完成，不是体验层完成**。
4. **v2 "待实施" 是真的待实施**：前端没有任何 v2 场景组件，Godot 项目为零，sprint1-mvp 分支也只是 v1 的旧快照。v2 完全停留在设计稿。

## 四、核心问题与风险

- **🔴 体验目标未达成（v2 核心诊断）**：宠物是静态 SVG 贴图、关卡本质是时间轴文本弹窗、只有答完一套题才给结算 —— 这正是 v1 被 v2 判为"鸡肋"的原因。功能齐全 ≠ 孩子爱用。
- **🔴 题库超纲且错位**：data.sql 中确认存在 G3 的**面积/周长/分数/小数/多位数乘法**等约 38 处超纲内容（如"正方形边长4厘米面积是多少"），与 v2 明确的"一年级"目标严重错位；同时 G1 仅 8 题，内容过薄。
- **🟠 测试极度薄弱**：5 个测试类 vs 25 控制器 + 28 表 + 367 题数据，任何重构都缺乏安全网。
- **🟠 dev 分支有未提交 WIP**：5 个文件改动游离，大重构前应先提交或 stash，避免污染。
- **🟠 无构建/CI 验证**：未实际跑过 `mvn compile` / `npm run build`，部署可靠性未知。
- **🟢 关键决策悬而未决**：v2 规定先用"凑十法"做 Svelte / Godot 双 Demo 让娃试玩定路径 —— 这一步是最高杠杆的动作，目前零进展。
